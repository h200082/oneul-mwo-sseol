# Firebase 방·공동 결과 3차 프로토타입 구현

- 날짜: 2026-07-31
- 도구·모델: Codex (세부 모델명은 최종 제출 문서 작성 시 실행 기록 기준으로 확정)
- 작업 목적: 로컬 방 프로토타입의 규칙을 유지하면서 서로 다른 기기에서 사용할 수 있는 Firebase 게이트웨이와 전원 공동 결과 화면을 구현하고, 권한 경계를 에뮬레이터로 검증
- 관련 파일·기능: `src/firebase/`, `src/bootstrap/createAppRuntime.ts`, `src/domain/roomResults.ts`, `src/rooms/`, `src/app/`, `src/game/`, `firestore.rules`, `firestore.indexes.json`, `firebase.json`, `.env.example`, `tests/`

## 주요 프롬프트·지시 사항

이전 단계에서 확정한 게임 규칙과 다음 구현 조건을 기준으로 사용했다.

- Firebase Anonymous Authentication의 `uid`를 참가자 ID로 사용
- `RoomGateway` 계약을 유지해 로컬 멀티탭과 Firebase 백엔드를 환경에 따라 선택
- 방 생성·참가·이탈·방장 시작을 Firestore 트랜잭션으로 처리
- 참가자 2~8명, 준비 버튼 없음, 시작 시 명단과 덱 시드를 잠금
- 방과 결과는 `onSnapshot`으로 실시간 구독
- 각 참가자의 결과는 점수, 최대 2개 포획 메뉴, 완료 시각만 제출하고 최초 제출 후 변경 불가
- 시작 때 잠긴 전원의 결과가 도착하기 전에는 진행 수를 표시하고, 모두 도착하면 공동 결과를 한 번에 공개
- 결과 화면에 1~8등, 동점 공동 순위, 각자의 포획 메뉴 카드와 빈 슬롯, 공동 1등, 가장 많이 겹친 메뉴, 공동 꼴찌를 표시
- Firebase 설정이 없는 개발 환경에서는 로컬 모드를 사용할 수 있게 하되, 명시적으로 Firebase를 요청하고 필수 값이 누락되면 오류 표시
- 실제 Firebase 프로젝트를 만들거나 배포하지 않은 상태를 구현 완료와 구분

대표 지시 요약:

> “익명 인증 `uid`를 플레이어 ID로 사용하고 Firestore 트랜잭션과 실시간 구독으로 기존 방 계약을 구현한다. 참가자별 결과는 한 번만 제출하고 전원 도착 뒤 공동 순위·포획 메뉴·겹친 메뉴·꼴찌를 공개한다. 로컬 대체는 유지하고 실제 프로젝트 미설정 상태를 명확히 기록한다.”

## 생성·제안 결과 요약

### Firebase 구성과 런타임 선택

- Firebase JavaScript SDK 12.16.0을 고정 버전으로 추가했다.
- `VITE_MULTIPLAYER_BACKEND`가 `local`이면 `LocalRoomGateway`, `firebase`이면 Firebase 런타임을 선택한다.
- 백엔드를 지정하지 않고 Firebase 필수 값이 전혀 없으면 로컬 모드를 사용한다.
- `VITE_FIREBASE_API_KEY`, `VITE_FIREBASE_AUTH_DOMAIN`, `VITE_FIREBASE_PROJECT_ID`, `VITE_FIREBASE_APP_ID` 중 일부만 있거나 Firebase를 명시했는데 값이 없으면 구성 오류를 낸다.
- Firebase 모듈은 실제로 필요할 때 동적 로드하고, 익명 로그인 완료 뒤 인증 `uid`를 `playerId`로 전달한다.
- `VITE_FIREBASE_USE_EMULATORS=true`이면 Auth 9099와 Firestore 8080 에뮬레이터에 연결한다.

### Firestore 방 게이트웨이

- `rooms/{roomCode}` 문서에 방장, 순서가 고정된 참가자 ID, 닉네임 맵, 식사 시간, 대기·시작 상태와 시작 데이터를 저장한다.
- 방 생성·참가·재접속·이탈·방장 승계·시작을 트랜잭션으로 처리한다.
- 방 코드는 최대 시도 횟수 안에서 충돌을 다시 생성하고, 시작 후 참가나 8인 초과는 도메인 규칙과 서버 규칙에서 거부한다.
- 방 문서 스냅샷을 기존 `Room` 도메인 값으로 변환하는 버전 1 코덱을 분리했다.
- 방 문서와 참가자별 결과 하위 컬렉션을 실시간 구독하고 화면 이탈 시 구독을 해제한다.
- 시작된 방의 잠긴 참가자가 새로고침하면 최초 결과 스냅샷을 한 번 확인해, 미제출 상태는 같은 식사 시간·덱의 게임으로, 제출 완료 상태는 결과 대기 또는 최종 요약으로 복귀한다.

### 결과 제출과 공동 결과

- 게임 장면은 방 플레이가 끝났을 때 `PlayerGameResult`를 실행당 한 번만 보고한다. 재시작한 판에는 새로운 보고기를 만든다.
- `rooms/{roomCode}/results/{uid}`에 본인의 결과만 생성할 수 있으며, 동일한 재전송은 멱등 처리하고 다른 값으로 고치는 것은 거부한다.
- 로컬 게이트웨이도 같은 결과 제출·구독 계약을 구현해 서버 없이 멀티탭 결과 흐름을 검증할 수 있게 했다.
- 시작 명단의 `N명 중 M명` 결과가 도착할 때까지 대기 화면을 표시하고 제출·구독 실패에는 재시도 동작을 제공한다.
- 전원 결과가 도착하면 순수 집계 함수가 표준 경쟁 순위(예: 공동 1등 다음 3등), 공동 1등·공동 꼴찌, 포획 슬롯, 최다 중복 메뉴를 만든다.
- 포획하지 않은 슬롯은 다른 메뉴로 자동 채우지 않고 빈 카드로 둔다. 두 개 이상의 메뉴가 같은 최대 중복 횟수면 모두 표시하고, 두 명 이상이 겹친 메뉴가 없으면 “겹친 메뉴 없음” 상태를 표시한다.
- 결과 화면은 메뉴를 도형 기반 이미지형 카드로 먼저 보여주고 아래에 작은 메뉴명을 표시한다.

### Firestore Security Rules

- 로그인하지 않은 요청과 방 컬렉션 목록 조회를 거부한다.
- 방 문서의 허용 필드, 코드 형식, 식사 시간, 1~8명 명단, 닉네임, 방장과 첫 참가자 일치를 검증한다.
- 본인 참가·재접속·이탈과 방장 시작에 필요한 필드만 바꿀 수 있게 상태 전이를 제한한다.
- 시작 시 최소 2명, 잠긴 명단, 콘텐츠 버전, 덱 시드와 서버 시각 범위를 검증한다.
- 시작 명단에 포함된 본인만 결과 문서를 만들 수 있고, 점수 범위와 최대 2개 고유 메뉴를 검증한다.
- 결과 문서의 수정·삭제를 거부하고, 결과 읽기는 해당 방 참가자에게만 허용한다.

## 사람의 검토 및 수정

- 인증 `uid`와 도메인 `playerId`가 다르면 클라이언트에서 먼저 거부하고 보안 규칙도 문서 경로의 `uid`를 다시 검증하도록 했다.
- Firebase 설정이 일부만 있는 상태에서 조용히 로컬 모드로 떨어지면 운영 오류를 숨길 수 있어 명시적 오류로 바꿨다.
- 참가 결과는 시작 시 잠긴 명단만 집계해 게임 중 새 참가자나 외부 결과가 순위에 섞이지 않게 했다.
- 결과 최초 제출을 불변으로 정하되 네트워크 재시도에서 같은 값은 성공으로 취급해 사용자가 중복 오류를 보지 않게 했다.
- 보안 규칙이 보장하는 범위는 본인 문서만 만들 수 있고 기존 결과를 바꿀 수 없다는 점까지다. 본인이 보내는 점수와 포획 메뉴가 실제 플레이에서 나온 값인지는 서버가 재계산하지 않으므로 부정행위 방지 시스템으로 보지 않았다.
- 동점은 임의로 승패를 나누지 않고 공동 순위를 유지하며, 명단 순서는 동점 안의 표시 순서에만 사용했다.
- 1등 메뉴를 자동 선택하거나 강요하지 않고, 1등의 포획 메뉴와 최다 중복 메뉴를 의사결정 정보로만 제공하도록 확정 기획을 유지했다.
- 포획하지 않은 사용자의 빈칸과 겹친 메뉴가 없는 경우를 정상 결과로 다뤘다.
- 웹 API 키는 Firebase 클라이언트 구성값이며 서비스 계정 비밀키와 다르다는 공식 안내를 확인했다. 데이터 보호 책임은 Authentication, Security Rules, API 제한과 운영 전 App Check 검토에 두고 서비스 계정 키는 클라이언트 환경 변수에 넣지 않도록 문서화했다.
- 로컬 백엔드 테스트와 Firestore Rules 에뮬레이터 테스트를 분리해 실제 클라우드 프로젝트를 건드리지 않고 권한 거부 사례를 반복 검증하게 했다.

## 검증 결과

| 검증 | 결과 | 확인 범위 |
|---|---|---|
| `npm run typecheck` | 통과 | Firebase 모듈, 게이트웨이 계약, 게임 결과 보고, 앱 결과 흐름의 타입 |
| `npm test` | 통과 | Firebase 구성·코덱·런타임 선택, 로컬 결과 제출·구독, 결과 집계와 게임 결과 1회 보고 |
| `npm run test:firebase-rules` | 통과 | 정상 방 생성·참가·시작·결과 읽기와 비인증·타인 조작·비방장 시작·타인의 결과 작성·기존 결과 수정·삭제 거부 |
| `npm run test:e2e` | 통과 | 로컬 멀티탭에서 게임·결과 대기 중 새로고침 복귀, 전원 결과 대기, 진행 수, 공동 결과 순위와 포획 메뉴 표시 |
| `npm run build` | 통과 | Firebase 동적 청크를 포함한 Vite 프로덕션 빌드 |

자동 검증은 로컬 게이트웨이와 Firebase Emulator Suite를 대상으로 한다. 시작한 방의 새로고침 복귀는 로컬 E2E로 검증했지만 라운드 진행 지점 자체를 저장하지는 않는다. 실제 Firebase 프로젝트, 운영 Security Rules, 인터넷 환경의 서로 다른 기기와 GitHub Pages 배포 URL은 아직 검증하지 않았다. 결과 미제출자의 제한 시간·기권 처리, 서로 다른 기기 시계를 서버 시간 오프셋으로 보정하는 시작 동기화, 제출 결과의 실제 플레이 일치 여부도 현재 검증 범위가 아니다.

## 제외한 내용 및 이유

- 실제 Firebase Console 프로젝트 생성·요금제 선택: 사용자 소유 계정과 프로젝트 결정이 필요한 외부 설정이므로 코드 작업과 분리
- 실제 웹 앱 구성값·GitHub 저장소 변수 등록: 아직 프로젝트가 없어 빈 `.env.example`만 제공
- 운영 Firestore Rules·인덱스 배포: 대상 프로젝트가 확정된 뒤 사용자 범위 안에서 실행해야 하므로 미수행
- 서로 다른 2~8대 휴대폰의 QR 참가·네트워크 지연·오프라인 복귀 테스트: 실제 프로젝트와 배포 URL 연결 후 수행
- App Check 강제 적용과 API 키 제한: 배포 도메인과 운영 정책이 확정된 뒤 적용
- 방 만료·비활성 방 정리: 해커톤 MVP의 한 판 흐름을 먼저 완성하기 위해 후속 운영 기능으로 유지
- 정확한 라운드 진행 지점 저장: 새로고침하면 같은 덱의 첫 라운드부터 재시작하며 중간 라운드·점수 복원은 후속 구현
- 결과 미제출자 제한 시간·기권 처리: 현재는 잠긴 명단 전원이 제출할 때까지 기다리므로 방치된 참가자 처리 정책이 필요
- 서버 시간 기반 시작 동기화: 현재 각 기기 시계로 `startAt`까지의 남은 시간을 계산하므로 실기기에서 시계 차이를 측정하고 서버 시간 오프셋 보정 필요
- 서버 판정·리플레이 검증: 현재 점수와 포획 메뉴는 본인 클라이언트가 제출하며 Security Rules는 작성자·형식·불변성만 검증
- 외부 음식 이미지·음성·사운드: 라이선스가 확정된 에셋을 별도 단계에서 추가하기 위해 이번 범위에서 제외
