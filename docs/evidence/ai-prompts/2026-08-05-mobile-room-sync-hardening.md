# 모바일 방 초대·로비 동기화 안정화

- 날짜: 2026-08-05
- 도구·모델: Codex (세부 모델명은 최종 제출 문서 작성 시 실행 기록 기준으로 확정)
- 작업 목적: 안드로이드에서 만든 방의 QR 초대 링크를 아이폰으로 열었을 때 로비 진입과 게임 시작 상태가 네트워크·캐시·비동기 처리 순서에 흔들리지 않도록 모바일 방 동기화 경로를 보강
- 관련 파일·기능: `src/app/AppController.ts`, `src/app/app.css`, `src/firebase/FirebaseRoomGateway.ts`, `tests/e2e/app-lobby-controller.spec.ts`, `tests/e2e-firebase/firebase-room-flow.spec.ts`, `tests/firebaseRules.integration.test.ts`, `playwright.firebase.config.ts`, `package.json`

## 주요 프롬프트·지시 사항

사용자가 설명한 실제 사용 흐름과 다음 안전 조건을 기준으로 진단·구현했다.

- 안드로이드에서 방을 만들고 QR을 아이폰으로 인식해 참가하는 흐름 점검
- 이미 정상 동작하는 게임 조작·점수·결과 기능은 변경하지 않고 방 초대와 로비 동기화 범위만 안정화
- 제공된 영상은 모두 성공한 실행이라는 사실을 유지하고, 최초 문제 상황은 녹화되지 않았으므로 영상만으로 특정 원인을 단정하지 않음
- QR 생성 실패나 지연이 방 명단 렌더와 Firestore 구독 시작을 막지 않게 함
- Firestore의 캐시 대기 상태가 서버의 시작 상태보다 늦게 도착해 화면을 되돌리지 않게 함
- 실시간 구독이 늦거나 끊겨도 제한된 재시도, 서버 직접 조회, 수동 복구 경로를 제공
- 방장 시작 요청은 실시간 listener의 반향만 기다리지 않고 트랜잭션 반환 상태도 즉시 사용
- 모바일 브라우저가 백그라운드에서 돌아오거나 네트워크가 복구될 때 최신 방 상태를 다시 확인
- 오래된 비동기 응답·구독 콜백·타이머가 새 화면이나 이미 시작된 게임을 덮어쓰지 않게 함
- 운영 Firebase 실기기 재검증과 GitHub Pages 재배포는 코드 구현 완료와 구분해 후속 단계로 기록

대표 지시 요약:

> “성공 영상에서 실패를 추정하지 말고, 기록되지 않은 최초 현상의 원인을 단정하지 않는다. 코드에서 확인되는 QR 생성과 구독의 비동기 순서, Firestore 캐시·서버 상태 경계, 시작 상태의 단조성, 재연결 경로만 보수적으로 강화하고 기존 게임은 유지한다.”

## 생성·제안 결과 요약

### 증거 범위와 코드상 취약 지점

- 제공된 모바일 영상들은 방 참가와 시작이 성공한 실행이었다. 최초로 보고된 실패 장면은 녹화되지 않아 특정 기기, 브라우저, 네트워크 또는 Firebase 캐시를 실제 원인으로 확정하지 않았다.
- 기존 `renderLobby()`는 QR 이미지 생성을 `await`한 뒤에야 방 구독을 시작했다. QR 캔버스 생성이 지연되거나 실패하면 명단 갱신과 시작 상태 수신까지 늦어질 수 있는 코드상 경쟁 경로를 확인했다.
- 이 경로는 보고된 최초 현상의 확정 원인이 아니라, 동일 증상을 만들 가능성이 있어 제거한 안정성 취약점으로 기록했다.

### QR과 로비 구독 분리

- 로비 기본 UI와 현재 명단을 먼저 렌더한 뒤 QR 생성과 방 구독을 서로 기다리지 않고 병렬로 시작하도록 순서를 바꿨다.
- QR에는 준비 중 상태를 표시하고, 생성에 실패하면 방 코드와 초대 링크를 사용할 수 있다는 대체 안내를 남긴다.
- QR 작업이 늦게 끝나더라도 화면 세대와 방 코드를 다시 확인해 이미 떠난 화면을 수정하지 않게 했다.

### 서버 기준 조회와 캐시 필터링

- `FirebaseRoomGateway.get()`은 기본 캐시 정책의 `getDoc()` 대신 `getDocFromServer()`를 사용해 복구 시 서버의 방 상태를 직접 확인한다.
- 방 구독은 metadata 변경을 포함해 수신하되 `fromCache` 또는 `hasPendingWrites`인 스냅샷은 로비 상태에 반영하지 않는다.
- 서버가 확정한 스냅샷을 받을 때만 동기화 상태를 `live`로 바꾸고 마지막 동기화 시각과 재시도 상태를 갱신한다.

### 제한 재시도와 사용자 복구

- 구독 시작 뒤 5초 안에 서버 스냅샷을 받지 못하면 watchdog이 복구를 시작한다.
- 구독 오류·방 누락·방 식별 불일치는 0.5초, 1.5초, 3초의 제한된 backoff로 서버 직접 조회와 재구독을 시도한다.
- 자동 복구 횟수를 모두 사용하면 오류 코드와 “다시 동기화” 버튼을 표시한다.
- 동기화가 `live`가 아닌 동안 방장의 시작 버튼을 비활성화해 오래된 명단으로 시작하지 않게 했다.

### 시작 상태의 단조성과 즉시 반영

- 현재 방이 한 번 `started`가 되면 뒤늦은 `waiting` 스냅샷을 무시해 상태가 역행하지 않게 했다.
- 이미 받은 시작 데이터와 다른 덱 시드·콘텐츠 버전·시작 시각·결과 마감 시각·잠긴 명단이 도착하면 충돌 상태로 보고 반영하지 않는다.
- 방장 시작 트랜잭션이 반환한 `StartedRoom`을 즉시 검증·반영하므로 실시간 listener 반향이 늦거나 오지 않아도 방장은 카운트다운으로 진행할 수 있다.
- listener와 시작 요청 반환이 같은 시작 상태를 거의 동시에 전달해도 동일 시작인지 비교해 중복 예약을 막는다.

### 모바일 복귀와 비동기 정리

- 페이지가 다시 보이는 `visibilitychange`와 네트워크 `online` 이벤트에서 서버 상태를 다시 읽고 방 구독을 연결한다.
- 두 이벤트가 동시에 발생하면 하나의 진행 중 조회를 공유해 중복 `get()`과 중복 구독을 만들지 않는다.
- 화면 세대, 방 코드, 연결 토큰을 확인해 이전 화면의 느린 조회와 구독 콜백을 무시한다.
- 로비 이탈·게임 시작 시 watchdog, 재시도 타이머, 구독, visibility·online 이벤트 핸들러를 정리하고 카운트다운 실행 직전에도 같은 시작 상태인지 다시 확인한다.

### 관찰 가능성

- 디버그 상태에 `phase`, `lastSyncedAt`, `retryCount`, `errorCode`를 포함한 `roomSync` 필드를 추가했다.
- 구독 시작, 서버 스냅샷 수락, 오래된 상태 무시, 복구 예약·소진, 시작 반환 수락을 `[room-sync]` 구조 로그로 남긴다.
- 사용자 화면에는 연결 확인 중, 복구 중, 복구 실패를 구분해 표시하고 내부 실패 코드를 함께 제공한다.

## 사람의 검토 및 수정

- 제공된 영상이 모두 성공 실행임을 다시 확인하고, 영상에 없는 최초 실패를 재현했다고 쓰거나 원인을 단정하는 표현을 제외했다.
- QR-before-subscribe 순서는 소스에서 직접 확인한 경쟁 경로로만 설명하고, 실기기 현상의 확정 원인과 구분했다.
- 캐시 스냅샷을 단순히 최신 상태로 취급하지 않고 서버 확정 스냅샷과 서버 직접 조회를 복구 기준으로 삼았다.
- `waiting`에서 `started`로의 전이는 단방향으로 유지하고, 서로 다른 시작 데이터는 조용히 덮어쓰지 않게 했다.
- 시작 버튼은 서버 상태가 확인된 `live` 단계에서만 사용할 수 있게 해 동기화 실패 중 중복 시작 요청을 막았다.
- QR 생성 실패는 방 자체의 실패로 처리하지 않고 방 코드·링크 대체 경로를 유지했다.
- 기존 베기·포획·점수·메뉴 덱·결과 집계 규칙은 이번 변경 범위에서 수정하지 않았다.

## 실제 반영 내용

- QR 생성과 로비 Firestore 구독의 독립 실행 및 QR 실패 대체 UI
- 서버 직접 방 조회와 캐시·로컬 미확정 스냅샷 필터링
- watchdog, 제한 backoff, 오류 코드, 수동 “다시 동기화” 기능
- 동기화 단계별 안내와 서버 확인 전 방장 시작 차단
- `started` 상태 역행 방지와 충돌하는 시작 데이터 거부
- 방장 시작 트랜잭션 반환 상태의 즉시 반영
- 모바일 foreground·online 복구와 중복 조회 병합
- 화면 세대·연결 토큰 기반 오래된 비동기 작업 차단 및 타이머·구독·이벤트 정리
- 방 동기화 디버그 상태와 구조 로그
- 로비 컨트롤러, Firestore late subscriber, Firebase 2클라이언트 자동화 테스트

## 제외한 내용 및 이유

- 최초 실패의 단일 원인 확정: 실패 장면과 당시 네트워크·콘솔·Firebase 상태 기록이 없어 증거보다 강한 결론을 피함
- 운영 Firebase 프로젝트에서 실제 안드로이드 방 생성 → 실제 아이폰 QR 인식 → 참가·동시 시작 재테스트: 최신 코드를 배포한 뒤 두 실기기로 확인해야 하므로 대기
- GitHub Pages 재배포와 공개 URL 검증: 이번 기록 시점에는 아직 수행하지 않았으므로 대기
- 실제 iOS Safari·Android Chrome의 백그라운드 복귀, 저속 네트워크, 오프라인→온라인 반복 측정: 운영 배포 뒤 실기기 검증 항목으로 유지
- 게임 조작·음식 이미지·사운드·점수·결과 규칙 변경: 정상 동작하는 게임을 보존하고 이번 문제 범위를 방 초대·로비 상태 동기화로 제한
