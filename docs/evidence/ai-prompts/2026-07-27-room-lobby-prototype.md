# 방·대기실 2차 프로토타입 구현

- 날짜: 2026-07-27
- 도구·모델: Codex (세부 모델명은 최종 제출 문서 작성 시 실행 기록 기준으로 확정)
- 작업 목적: 1인 코어 게임 앞에 실제 서비스 형태의 홈·방 생성·참가·대기실 흐름을 연결하고, 서버 연동 전에 방 규칙과 공통 게임 시작 조건을 검증
- 관련 파일·기능: `src/app/`, `src/domain/room.ts`, `src/rooms/`, `src/qr/`, `tests/room*.test.ts`, `tests/localRoomGateway.test.ts`, `tests/qrScanner.test.ts`, `tests/e2e/room-flow.spec.ts`

## 주요 프롬프트·지시 사항

사용자가 확정한 다음 요구를 구현 기준으로 사용했다.

- 홈에서 점심·저녁만 고르고 혼자하기 또는 방 만들기로 진입
- 최대 8인 방과 8자리 방 코드, 초대 링크, 실제 QR 이미지 제공
- 앱 안에서 QR을 인식하되 기능 미지원 시 링크·방 코드 입력으로 대체
- 참가자별 준비 상태와 준비 버튼을 만들지 않음
- 방장을 포함해 2명이 모이면 방장이 즉시 시작 가능
- 시작 시 3초 카운트다운 후 모든 참가자가 같은 `deckSeed`와 20개 메뉴 덱 사용
- 실제 Firebase 연동 전에는 같은 출처의 멀티탭에서 방 흐름을 검증

## 구현 결과

### 홈과 게임 진입

- `AppController`가 DOM 홈, 점심·저녁 선택, 혼자하기, 방 만들기, 방 참가, 대기실, 카운트다운, Phaser 게임 마운트를 연결한다.
- 혼자하기와 방 게임 모두 선택한 식사 시간과 명시적 덱 시드를 `GameHost`에 전달한다.

### 방과 대기실

- `src/domain/room.ts`에 2~8인 인원 제한, 방장 권한, 8자리 코드, 준비 상태가 없는 참가자 목록, 시작 상태와 공통 덱 시드 규칙을 분리했다.
- `RoomGateway` 인터페이스와 `LocalRoomGateway` 구현을 나눠 다음 단계에서 Firebase 구현으로 교체할 수 있게 했다.
- 현재 구현은 `localStorage`에 방을 저장하고 `BroadcastChannel`을 우선 사용하며, 지원되지 않을 때 브라우저 `storage` 이벤트로 같은 출처의 다른 탭을 갱신한다.
- 방장은 참가자가 2명 이상이면 시작할 수 있고, 모든 탭은 동일한 시작 시각을 기준으로 3초 카운트다운 뒤 같은 `deckSeed`와 동일한 20개 메뉴 덱으로 진입한다. 대기 중 참가자가 나가면 `rosterOrder`를 연속으로 다시 매기고, 방장이 나가면 가장 먼저 참가한 남은 인원이 승계하며, 마지막 참가자가 나가면 저장된 방을 삭제하고 다른 탭에 삭제를 알린다.
- 대기실 진입 시 URL에 `room` 코드를 유지하고, 새로고침 뒤 같은 세션의 `playerId`가 다시 참가하면 인원을 추가하지 않고 기존 자리로 멱등 복귀한다.

### QR 초대와 스캔

- `qrcode` 1.5.4로 실제 초대 URL을 PNG data URL QR 이미지로 생성한다.
- 초대 링크의 `room` 검색 매개변수와 직접 입력한 코드를 동일한 정규화·검증 함수로 처리한다.
- 앱 내 카메라 스캔은 브라우저의 `BarcodeDetector`가 QR 형식을 지원할 때만 활성화한다.
- `BarcodeDetector` 미지원, 카메라 권한 거부, 제한 시간 초과 때는 초대 링크 또는 8자리 방 코드를 입력하도록 안내한다.

## 사람의 검토 및 수정

- 헷갈리는 문자 `0`, `1`, `I`, `L`, `O`를 방 코드 문자 집합에서 제외했다.
- 준비 버튼 없이 2명부터 방장만 시작할 수 있고 참가자는 시작할 수 없도록 권한을 확인했다.
- 중복 참가, 8인 초과, 시작한 방 참가, 손상된 로컬 저장 데이터 등 실패 경로를 단위 테스트에 포함했다.
- QR 이미지가 실제 `data:image/png;base64` 형식인지, 초대 URL의 소문자 코드도 정규화되는지 확인했다.
- 두 브라우저 탭이 저녁 설정, 공통 `deckSeed`, 동일한 20개 메뉴 순서를 공유하는지 E2E로 확인했다.
- 게임 재시작 시 `resetRunState()`가 활성·일시정지 토큰, 제스처 타이머, 포인터, 경로, 라운드, 덱, 진행 플래그를 모두 초기화해 이전 판 상태가 다음 판에 남지 않게 했다.
- 멀티터치에서는 첫 입력의 `activePointerId`만 제스처 종료·취소까지 추적하고 다른 포인터 입력을 무시해 하나의 경로에 여러 손가락이 섞이지 않게 했다.
- QR 스캔은 `AbortController`로 이전 스캔·화면 이탈·앱 종료를 취소하고, 성공·오류·취소 모두에서 비디오를 멈추고 `srcObject`를 비운 뒤 모든 카메라 트랙과 오버레이를 정리한다.
- 비동기 QR 생성과 방 구독에는 로비 화면의 `viewGeneration`을 대조해 이미 떠난 화면의 완료 결과·콜백을 무시하고, 늦게 생성된 구독은 즉시 해제한다.
- 방 시작 데이터에 `contentVersion`을 저장하고 로컬 콘텐츠 버전과 일치할 때만 카운트다운과 게임을 예약해 서로 다른 메뉴 데이터 버전의 참가자가 같은 덱이라고 오인하지 않게 했다.
- 메뉴가 기준선을 지나 미스가 확정될 때도 제스처 타이머, 그리기 상태, 활성 포인터, 경로, 일시정지 토큰, 트레일을 초기화해 다음 메뉴 입력에 이전 제스처가 섞이지 않게 했다.
- 방 생성·참가마다 고유 `Symbol` action token과 홈 화면 세대를 함께 저장하고, 요청 중에는 solo/create/join을 모두 잠그며 느린 응답이 최신일 때만 로비·버튼 상태를 변경하도록 했다.
- 방 나가기·재접속 테스트로 명단 재정렬, 방장 승계, 마지막 방 삭제와 URL을 유지한 동일 `playerId` 멱등 복귀를 확인했다.

## 현재 한계

Firebase 프로젝트, SDK, 인증, Firestore, 보안 규칙은 아직 코드와 실행 환경에 연결하지 않았다. 현재 방 데이터는 동일 브라우저 출처의 `localStorage`에만 존재하므로 다음 기능은 아직 동작하지 않는다.

- 서로 다른 휴대폰·PC의 실제 방 참가와 상태 동기화
- 새로 접속한 기기의 서버 기반 방 조회
- 익명 사용자별 권한과 방장 권한의 서버 검증
- 동시 참가·시작 요청을 보호하는 Firestore 트랜잭션과 서버 원자성
- 연결 해제, 재접속, 방 만료의 서버 처리
- 참가자별 점수·포획 메뉴를 서버에 모으는 공동 결과 집계

따라서 다른 기기에서 QR을 스캔하면 링크와 방 코드는 전달되지만, 해당 기기의 로컬 저장소에는 방이 없어 참가할 수 없다. 이 제한은 UI 문제가 아니라 서버 게이트웨이가 아직 없는 2차 프로토타입의 의도된 경계다.

| 익명 인증 | `signInAnonymously`로 임시 사용자 계정을 만들고 보안 규칙과 함께 사용 가능 | 닉네임과 별개로 안정적인 `uid`를 참가자·방장 식별자로 사용 |
| 실시간 상태 | `onSnapshot`은 최초 스냅샷과 이후 변경을 실시간 전달 | 방 문서 또는 참가자 쿼리를 구독해 대기실·시작 상태 갱신 |

## 제외한 내용 및 이유

- Firebase SDK·프로젝트 설정·실기기 방: 사용자 소유 Firebase 프로젝트와 보안 규칙을 준비한 뒤 별도 단계에서 구현하기 위해 제외
- 카메라 QR 라이브러리 폴리필: 브라우저 번들과 권한 복잡도를 늘리지 않고 링크·코드 대체 경로를 먼저 검증하기 위해 제외
- 준비 버튼: 직접 모인 사용자가 빠르게 시작한다는 확정 기획에 따라 의도적으로 제외
- 공동 결과 집계·재접속: 실제 서버 상태 모델, 트랜잭션, 보안 규칙이 정해진 뒤 구현하기 위해 다음 단계로 유지
