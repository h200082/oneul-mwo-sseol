# 오늘 뭐 썰? — 개발 및 제출 로드맵

> 문서 버전: 1.0
> 작성일: 2026-07-27
> 기준 기획서: `docs/source/game-design.md` v1.1
> 일정 기준: 마감일 미정, 1인 전일 작업 약 12~18일

## 1. 현재 상태

| 영역 | 상태 | 다음 조치 |
|---|---|---|
| 게임 기획 | v1.1 확정 | 구현 중 변경은 결정 기록에 남김 |
| 제출 문서 구조 | 준비됨 | 개발과 동시에 내용 갱신 |
| Git 저장소 | 로컬 `main`, 초기 파일 스테이징 | 작성자 정보 설정 후 기준선 커밋 |
| 원격 저장소 | 없음 | 공개 GitHub 저장소 생성·연결 |
| 게임 코드 | 없음 | Vite·TypeScript·Phaser 초기화 |
| 웹 배포 | 없음 | 초기 화면부터 GitHub Pages 시험 배포 |
| Firebase | 없음 | 개발·운영 환경과 보안 규칙 구성 |
| 음식·배경·음향 | 기획만 완료 | 규격 확정 후 대표 에셋부터 제작 |
| 최종 PDF·영상 | 없음 | 출시 후보 동결 후 제작 |

## 2. 제작 원칙

1. 핵심 재미인 베기·포획 판정을 가장 먼저 검증한다.
2. 대표 음식 5개로 스타일과 판정을 통과한 뒤 나머지 45개를 제작한다.
3. 멀티플레이를 후반까지 미루지 않고 실제 휴대폰 2대로 조기에 검증한다.
4. 모든 네트워크 플레이어에게 서버가 확정한 동일한 20개 덱을 제공한다.
5. 개발 중 생성한 AI 결과와 외부 에셋은 그날 바로 출처를 기록한다.
6. P0가 안정화되기 전에는 업적·추가 도구·AI 음성 같은 확장 기능을 시작하지 않는다.
7. 제출 영상과 PDF는 최종 배포 버전을 기준으로 제작한다.

## 3. 우선순위

### P0 — 제출에 반드시 필요한 기능

- 모바일·데스크톱에서 실행되는 웹 게임
- 멈춤 없는 드래그 베기와 길게 누르기 포획 판정
- 절단 면적 정확도와 평균 점수
- 한국 일상 메뉴 50개 중 동일한 20개 출제
- 포획 0~2회와 놓침 0점 처리
- 1인 플레이
- QR·링크·코드로 참가하는 2~8인 방
- 방장 시작, `waiting → preparing → started`, 명단 잠금, 전원 자동 준비, 동일 덱, 4초 카운트다운
- 1~8위 결과와 참가자별 포획 메뉴 이미지
- 최다 겹침 메뉴와 고정 식사 내기 결과
- 팝 아케이드 다이닝 테이블 기본 배경
- 첫 실행 ON인 효과음·BGM 마스터·진동·나레이션과 명시적 OFF 저장
- 홈에서만 여는 별도 비채점 베기·포획 튜토리얼
- GitHub Pages 공개 배포
- 게임 소개 PDF, AI 활용 PDF, 30~60초 실제 플레이 영상

### P1 — P0 안정화 후 추가

- 결과 카드 공유
- 도구 스킨 1개
- 업적 2~3개
- 대표 AI 음성 5~8개
- 개인 최고 기록
- 추가 베기·포획 파티클

### P2 — 제출 이후

- 디저트 전용 모드
- 음식별 복수 이미지
- 대규모 업적·칭호
- 팀전
- 인앱결제
- 주변 음식점 연결

## 4. 전체 제작 순서

```text
M0 저장소 기준선
  ↓
M1 실행·배포 골격
  ↓
M2 핵심 판정 및 2인 연결 위험 검증
  ↓
M3 1인 수직 프로토타입
  ├──────────────┐
  ↓              ↓
M4 콘텐츠 제작   M5 전체 멀티플레이
  └──────┬───────┘
         ↓
M6 결과·전체 UX
  ↓
M7 연출·성능 안정화
  ↓
M8 출시 후보 QA
  ↓
M9 영상·PDF·최종 제출
```

## 5. 단계별 작업과 완료 조건

### M0. 저장소 기준선 — 약 0.5일

목표: 앞으로의 모든 변경을 커밋으로 추적할 수 있게 만든다.

작업:

- Git 작성자 이름·이메일 설정
- 현재 기획서와 제출 구조를 첫 기준선 커밋으로 기록
- 공개 GitHub 저장소 생성 및 `origin` 연결
- 프로젝트 제목과 기술 스택으로 `README.md` 갱신
- 이슈 또는 작업 보드에 P0·P1·P2 등록
- 개인 참여 여부 확정

완료 조건:

- `main`에 첫 커밋이 존재한다.
- 원격 저장소에서 전체 문서를 확인할 수 있다.
- 커밋되지 않은 의도치 않은 파일이 없다.

### M1. 실행·배포 골격 — 약 1일

목표: 빈 화면이라도 실제 휴대폰에서 공개 URL로 실행되는 상태를 만든다.

작업:

- Vite, TypeScript, Phaser 프로젝트 초기화
- Vitest와 Playwright 기본 구성
- 세로 화면 우선 반응형 캔버스와 safe-area 처리
- 마우스·터치 입력 공통 인터페이스 구성
- `.env.example`과 환경변수 정책 작성
- GitHub Actions 빌드와 GitHub Pages 시험 배포
- 새로고침·직접 URL 접근 시 404가 나지 않도록 라우팅 구성

완료 조건:

- 로컬에서 설치·개발·테스트·빌드 명령이 동작한다.
- 공개 URL을 시크릿 창과 실제 휴대폰에서 열 수 있다.
- 저장소에 비밀키가 포함되지 않는다.

### M2. 핵심 위험 검증 — 약 2일

목표: 가장 실패 가능성이 큰 입력 판정과 온라인 입장을 먼저 증명한다.

#### M2-A. 베기·포획 기술 시제품

- 임시 음식 실루엣과 분리된 표준 판정 마스크 낙하
- 드래그 경로 수집·보간·시각화
- 음식 안쪽 시작·종료도 허용하는 열린 드래그 베기 판정
- 0.32초 길게 누르기 포획과 14px 이동 시 베기 전환
- 베기 선 기준 양쪽 면적 계산
- 50:50, 60:40, 75:25 점수 검증
- 포획 성공·실패와 슬롯 소모 규칙
- 디버그 오버레이로 궤적·교차점·면적 표시

판정은 음식 그림의 복잡한 알파 외곽선이 아니라 모든 메뉴에 동일한 표준 원형 마스크를 사용한다. 화면에는 원형 크롭을 강제하지 않고 투명 음식 실루엣을 원본 비율로 표시한다.

#### M2-B. 2인 방 연결 시제품

- Firebase 익명 인증
- 임시 방 생성
- QR·초대 링크·8자리 코드 참가
- 방장과 참가자가 같은 방 상태를 확인
- 카메라 권한 거부 시 링크·코드 입장 대체 경로

완료 조건:

- Android Chrome과 iPhone Safari에서 길게 누르기와 드래그가 충돌 없이 구분된다.
- 연속 30회 입력 후 조작이 멈추거나 페이지가 스크롤되지 않는다.
- 자동 테스트에서 기준 절단 점수가 정의와 일치한다.
- 서로 다른 두 기기가 QR 또는 코드로 같은 방에 들어간다.

실제 iPhone이 없으면 해당 항목을 출시 후보 전 필수 외부 테스트로 남긴다.

### M3. 1인 수직 프로토타입 — 약 2일

목표: 임시 그래픽으로 한 판을 처음부터 끝까지 플레이한다.

작업:

- 메뉴 데이터 구조와 고유 `menuId`
- 50개 풀에서 중복 없는 20개 덱 생성
- 점심·저녁 가중치
- 메뉴 등장·낙하·베기·포획·놓침 상태
- 포획 0개·1개·2개의 평균 분모 20·19·18
- 놓친 비포획 메뉴 0점
- 홈 `튜토리얼 하기`에서만 실행하고 완료·다시 연습·홈 이동을 제공하는 비채점 베기·포획 튜토리얼
- 개인 결과와 다시 하기
- 핵심 규칙 단위 테스트

완료 조건:

- 한 판을 10회 연속 오류 없이 끝낼 수 있다.
- 포획하지 않아도 정상적으로 결과 화면이 나온다.
- 동일한 덱 데이터로 항상 같은 순서와 조건이 재현된다.
- 대표적인 점수·포획·놓침 테스트가 자동화되어 있다.

### M4. 콘텐츠·아트·사운드 — 약 3~5일, M3 이후 일부 병렬

목표: 재작업 없이 50개 콘텐츠를 일관된 규격으로 완성한다.

#### 공통 규격

- 원본: 투명 배경 PNG, 긴 변 기준 1024px, 실루엣에 맞춘 타이트한 크롭
- 런타임: 투명 WebP, 긴 변 기준 최대 512px, 원본 가로세로 비율 유지
- 음식 그림: 원형 크롭을 사용하지 않고 가로형·세로형·불규칙형 실루엣과 6~10% 투명 안전 여백 유지
- 음식당 권장 용량: 120KB 이하
- 글자·브랜드·로고·유명 캐릭터 없음
- 동일한 시점·광원·외곽선

#### 제작 순서

1. 메뉴 50개의 ID·이름·분류·점심/저녁 가중치 확정
2. 현재 임시 5종으로 원본 비율 표시, 베기 표현, 결과 썸네일, 로딩 성능 검증
3. 메뉴 50종 전체의 실루엣·구도·투명 여백 규격을 표로 확정
4. 조작과 표시 규격 승인 후 동일 작업 묶음에서 50종을 생성·선별·후처리
5. 팝 아케이드 다이닝 테이블 배경 레이어 제작
6. 버튼·등장·베기·포획·놓침·결과 효과음 제작
7. BGM 1곡과 결과 스팅어 제작
8. 각 에셋의 프롬프트·출처·라이선스·사람의 수정 내용 기록

완료 조건:

- 정확히 50개의 고유 메뉴와 이미지가 연결된다.
- 결과 화면의 작은 이미지에서도 메뉴가 식별된다.
- 모든 메뉴가 동일한 판정 마스크와 난도를 사용한다.
- 한 판에서 불러오는 20개 음식 이미지가 목표 용량 안에 있다.
- 배경이 음식·궤적·점수보다 먼저 눈에 띄지 않는다.
- 외부 에셋과 AI 생성물의 증빙이 빠짐없이 기록된다.

### M5. 전체 멀티플레이 — 약 2~3일

목표: 최대 8명이 공정하게 같은 판을 시작하고 결과를 제출한다.

작업:

- 방 생성·QR·링크·코드 참가
- 최대 8명 슬롯과 9번째 참가 거부
- 2명 이상일 때 방장 시작 활성화
- 방장 시작 시 `waiting → preparing`으로 전환하고 참가 명단과 설정 잠금
- 서버가 확정한 20개 덱과 콘텐츠 버전 저장
- 참가자별 제한 시간 프리로드와 폴백 확정 후 자동 준비 완료 전송
- 전원 준비 후 `preparing → started`와 공통 `startAt` 기준 4초 카운트다운
- 자동 연습 없이 모든 참가자가 원래의 20개 라운드에 바로 진입
- 로컬 게임 실행과 실전 진행도·완료·결과만 네트워크 전송
- 늦은 입장 차단
- 재접속·방장 이탈·미완주·결과 재전송 처리
- Firebase 보안 규칙과 만료 방 정리

완료 조건:

- 2·4·8인 테스트에서 모든 기기의 덱 해시가 같다.
- 사용자용 준비 버튼 없이 모든 잠긴 참가자의 자동 준비 완료가 확인된 뒤 시작된다.
- 일시적인 연결 끊김 후 결과가 재전송된다.
- 각 사용자는 허용된 자신의 데이터만 수정할 수 있다.
- 결과를 임의로 반복 제출해 변경할 수 없다.

### M6. 결과·전체 UX — 약 1~2일

목표: 게임이 제공해야 하는 순위와 취향 정보를 한 화면 흐름으로 완성한다.

작업:

- 홈·식사 시간 선택·방 만들기·대기실·플레이·결과 화면
- 1~8위와 평균 정확도
- 플레이어별 포획 이미지 0~2개
- 포획하지 않은 슬롯의 빈 카드
- 1등의 포획 메뉴
- 동일 `menuId` 기준 최다 겹침 메뉴
- 겹침 없음·아무도 포획하지 않음 상태
- 공동 순위와 공동 최다 처리
- `꼴찌가 1등의 식사를 부담해요` 결과 문구
- 솔로의 같은 메뉴 다시 하기·새 메뉴·홈, 방의 안전한 새 메뉴·홈 이동
- 같은 방 재대결은 시작 회차별 결과 저장과 참가자 재동의 상태 전이를 갖춘 후속 기능으로 분리

완료 조건:

- 모든 참가자 기기에서 순위와 요약 결과가 같다.
- 부담자와 수혜자가 뒤바뀌지 않는다.
- 공동 1등·공동 꼴찌에는 참가자 합의 안내가 나온다.
- 게임이 최종 메뉴를 자동 확정하지 않는다.

### M7. 연출·성능 안정화 — 약 1~2일

목표: 핵심 동작을 명확하고 즐겁게 보이게 하되 저사양 기기에서도 안정화한다.

작업:

- 베기 궤적·두 조각 분리·정확도 팝업
- 포획 링·회전·슬롯 이동
- 칼각·놓침·결과 연출
- 팝 아케이드 다이닝 테이블의 점심·저녁 조명 오버레이
- BGM·효과음 마스터, 진동, 나레이션의 첫 실행 ON·명시적 OFF 저장·브라우저 오디오 잠금 해제
- 이미지 압축, 객체 풀링, 파티클 수 제한
- 화면 회전 시 세로 모드 안내
- P0 안정화 후에만 P1 기능 중 효과 대비가 큰 항목 선택

완료 조건:

- 입력 후 100ms 안에 시각 피드백이 시작된다.
- 일반 플레이가 모바일에서 최소 30fps, 목표 45~60fps를 유지한다.
- 프리로드가 느리거나 일부 자산이 실패해도 제한 시간 폴백으로 무한 대기 없이 같은 판정을 유지한다.
- 연출이 다음 음식이나 HUD를 가리지 않는다.

## 8. 마감일 기준 동결 일정

마감일을 `D`라고 할 때 다음 역산 일정을 사용한다.

- `D-7`: 기능 동결
- `D-6`: 콘텐츠·라이선스 동결
- `D-5`: 전체 자동 테스트와 2·4·8인 테스트
- `D-4`: 출시 후보 배포
- `D-3`: 최종 버전 확정 및 코드 동결
- `D-2`: 실제 플레이 영상과 PDF 완성
- `D-1`: 외부 기기 제출 리허설
- `D-day`: 조기 제출 및 링크 보존

최종 코드가 바뀌면 재배포, 영상 재촬영 필요 여부 판단, PDF 링크 검수를 다시 수행한다.

## 9. 바로 시작할 작업

1. Git 작성자 이름·이메일을 설정한다.
2. 현재 문서 기준선을 첫 커밋으로 남긴다.
3. 공개 GitHub 저장소를 만들고 `origin`을 연결한다.
4. Vite·TypeScript·Phaser와 테스트 도구를 초기화한다.
5. GitHub Pages에 빈 게임 화면을 시험 배포한다.
6. 투명 음식 실루엣과 표준 판정 마스크를 분리한 베기·길게 누르기 포획 디버그 시제품을 만든다.
7. 실제 Android와 iPhone에서 입력을 검증한다.
8. 메뉴 50개 목록과 전체 실루엣·구도 규격을 확정하고 최종 이미지는 조작 승인 뒤 일괄 제작한다.

첫 번째 플레이 가능 목표는 다음 한 문장으로 정의한다.

> 공개 URL을 휴대폰에서 열어 임시 음식 20개를 베거나 최대 2개 포획하고, 정확한 평균 점수와 결과를 확인할 수 있다.
